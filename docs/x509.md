# Lane 3: x509 (DER, PEM, certificates, chain validation, private keys)

Code in `src/tls/x509/`: `der.mojo` (strict reader), `pem.mojo`, `cert.mojo` (`Certificate.parse`), `chain.mojo`
(`verify_chain`, `host_matches`, `load_system_roots`), `sigs.mojo` (`verify_sig`), `key.mojo` (`load_private_key`).
Hashes come from `tls.sym`, RSA and ECDSA verification from `tls.asym`. `psl.mojo` is generated by `tools/gen_psl.py`.

## What verify_chain enforces
- Chain input leaf first, at most 40 certificates, any order of intermediates; the root may be present or absent.
- Path found by names (at most 4096 search steps), structural rules run, then signatures verify top-down from the
  trusted root (a key the peer supplied is used only after the root vouched for it). At most 16 candidate paths per call.
- Validity at the caller's `now` (inclusive), unknown critical extensions (anchor included), duplicate extensions,
  signature algorithm equal inside and outside the TBS, cA and keyCertSign agreement, pathLen (self-issued intermediates
  not counted), intermediate EKU, DNS and IP name constraints (self-issued intermediates skipped, wildcard SANs checked
  against the excluded subtrees they cover), name types it cannot check fail closed.
- Extension profile (RFC 5280 plus CA/B BR where limbo asks): serial positive, non-zero, at most 20 octets (not checked on
  the anchor: GoDaddy and Hellenic roots have serial 0); SKI and AKI never critical; CA certificates (and the anchor) need
  an SKI; every certificate that is not self-issued needs an AKI keyIdentifier; a self-issued anchor's AKI is its SKI
  alone; CA basicConstraints critical, also in the anchor, which must have one; nameConstraints critical and only in CA
  certificates, no leading period in a dNSName constraint; policyConstraints critical; AIA well formed and non-critical.
- `verify_chain(..., client=True)` (wave 3b, client certificates): the same path rules with clientAuth (or anyExtendedKeyUsage) instead of serverAuth on the leaf and on every intermediate that has an EKU, and no host name check; the SAN rules still apply when a SAN is present.
- Leaf: not a CA, serverAuth in an extendedKeyUsage (required), digitalSignature if keyUsage is present, SAN critical
  exactly when the subject is empty, every dNSName in preferred name syntax (no underscore), wildcard never over a
  public suffix (embedded PSL, ICANN and private rules, multi-label; IDN rules match as punycode), key P-256, P-384 or
  RSA >= 2048 bits with a size that is a multiple of 8.
- Refused: SHA-1 signatures, RSA issuer keys below 2048 bits, RSA-PSS with a hash/MGF1 mismatch, leaf keys the supported
  suites (P-256, P-384, RSA) cannot use.
- Resource caps (nc-dos): 1024 SAN names and 256 name constraint subtrees per certificate (a parse error above that),
  so a constraint check is at most 256 x 1024 comparisons per certificate pair. Tested by chain cases
  `ok_caps_at_limit`, `bad_nc_257_subtrees`, `bad_san_1025_names`, limbo `pathological::nc-dos-*`, mutants
  `nc_subtree_cap_removed`, `san_cap_removed`, `dos_caps_all_removed`.
- Hostname: SAN only (RFC 9525), never the CN (test `bad_cn_victim`: CN=victim.example, SAN=other.example does not verify
  for victim.example). IP literals match iPAddress only. Wildcard: whole left-most label, at least two labels after it.
  One trailing dot on the host is ignored.
- Trust anchors: only the profile above and cA/keyCertSign/pathLen/name constraints are processed. `anchor_rules` runs over
  the system bundle in `gate_x509.sh roots` (117 of 118 pass; TWCA Global Root CA has no SKI and is refused as an issuer).

## x509-limbo (tests/limbo_known.txt, `gate_x509.sh limbo`)
9748 cases: 9731 agree. Invalid chains accepted: 9, all `webpki::cn::*`, pinned as policy (the CN is never read).
Valid chains rejected: 8, each with a reason in the file: ML-DSA keys (3, no verifier), and five where limbo itself
conflicts with an invalid case (CA certificate as leaf x2, leaf without EKU, non-critical name constraints, an anchor
without AKI under a different issuer). The gate fails on any other disagreement, and a `!` pin is only accepted for
`webpki::cn::`. Invalid wins every conflict.

## Not done
Revocation, policies, AIA fetching, SCTs, IPv4-mapped IPv6 host literals, IDN normalisation (the PSL is matched as
punycode, no case folding beyond ASCII), ECDSA with P-521, Ed25519 certificates, ML-DSA, encrypted private keys,
multi-prime RSA, leaf validity length limits. The step bound of the path search has no test that reaches it.
